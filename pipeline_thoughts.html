1. Project Context

The CA3 Final Project (Customer Engagement & Artificial Intelligence, H9CEAI) requires building an Agentic Organisation — a five-agent pipeline (Researcher, Designer, Maker, Communicator, Manager) that collaboratively solves a real customer-engagement problem. The chosen domain: Irish primary teachers overwhelmed by curriculum-aligned resource discovery.

The solution must demonstrate:

  • An unbroken handoff chain where each agent's output becomes the next agent's real input (25% of grade)
  • At least one agent connecting to a live external data source via MCP/API at run time
  • A catalogue taxonomy capable of multi-dimensional tagging across subject, grade, format, season, pedagogy, and source

The initial content corpus is a teacher's manually curated Teaching Resources folder — ~4,850 files built up over years of classroom practice. This document captures the exploration from naive folder-based categorisation through to a costed, benchmarked plan for full-content indexing.

3. Phase 1 — Naive Folder-Level Categorisation

Where we started

The first pass treated the folder structure as the taxonomy. Each folder was mapped to a category, sub-categories inherited from subdirectories. This produced the initial CATALOGUE.md — 20 top-level categories covering Literacy (~1,800 files), Mathematics (~545), SESE (~95), Gaeilge (~119), SEL (~338), and so on.

What folder-level gave us

  • Instant scan — 30 seconds for 4,398 files
  • 3–4 reliable tags per file (subject, sub-domain, season from folder path)
  • Clean top-level structure matching Irish primary curriculum areas
  • Multi-category detection where folders cross-cut (e.g. xmas/Maths/)

What folder-level missed

  • Duplicate detection: Free Fall Bundle (4).pdf and Free Fall Bundle (4) 1.pdf are identical content — invisible from names alone
  • Content type: Is it a lesson plan, a worksheet, a game, or a poster? The folder says "maths" but not "write-the-room counting centre"
  • Grade band: Most folders mix infants through 6th class with no signal in the path
  • Pedagogy: SOR-aligned? Play-based? Differentiated? Invisible
  • Source & licensing: Teachers Pay Teachers single-classroom licenses — critical for the regulatory/ethics section
  • UUID filenames: 3.5% of PDFs have names like 941dbfe6-b2bb-4ebe-bc7c-2fde69145b77.pdf — zero signal

A folder-level approach tags ~30% of the useful dimensions for a teacher query like "morphology games for seniors around Christmas". It gets morphology (folder) and Christmas (folder), but misses game (content type), seniors (grade band), and whether it's SOR-aligned (pedagogy).

6. Phase 4 — The Image-Heavy PDF Problem

The real bottleneck

30% of PDFs (996 files) yield fewer than 500 characters of extractable text. These are predominantly:

  • Scanned/photographed worksheets where the instructional content is in the picture
  • Craft templates (cut-and-paste, colour-by-number, tracing sheets)
  • Classroom posters and display materials
  • Activity cards and game boards where structure is visual

Standard pdfplumber text extraction gets almost nothing from them because there is no embedded text layer. The value a teacher would search for — "CVC word sort with pumpkin theme for infants" — is visually obvious to a human but invisible to a text parser.

Case study: Just Add Words Fall (14 pages)

  • Pages 1–4: Introduction, terms, author bio — 1,200 chars of extractable text
  • Pages 5–14: The actual picture writing prompts — 0 chars (just a copyright footer)
  • All the instructional value is in the images: a scarecrow scene, a pumpkin patch, autumn leaves
  • A text-only parser learns it's "about fall writing" but completely misses that it's 10 distinct scene-based prompts

The Gemini Flash vision path (Option 4) is the most compelling for image-heavy PDFs because:

  1. At $2.50–12.50 for all 996 PDFs, it's in the same cost ballpark as cloud OCR ($37) but with orders of magnitude less engineering (no OCR pipeline to build or tune)
  2. It captures pedagogical intent — "this is a write-the-room counting centre for PreK-K" — that OCR text alone cannot express
  3. It handles the worst case (craft templates with zero words) gracefully — the model can still describe the activity from the visual layout
  4. Prompt engineering: send the image with "Describe this teaching resource. Output JSON with: subject, subdomain, grade_band, format, activity_type, season, pedagogy_flags, requires_preparation"

For the 70% text-rich PDFs, DeepSeek classification on extracted text is perfectly adequate and trivially cheap ($3.10). The prompt would similarly request structured JSON output from the extracted text content.

9. Open Design Decisions

Decision 1: Parse depth — full or optimised?

At $4.85 vs $0.55 total API cost, money isn't the deciding factor. The question is: does the engineering effort to build the full pipeline (ZIP extraction, nested recursion, error handling for 5,000+ files) justify the 3–5 extra tags per file? For the CA3 deliverable — where the rubric values demonstrated handoffs and live data over catalogue completeness — the optimised approach (folder-pass + deep-parse only gaps) is likely the right tradeoff. The full deep parse can be named as "production path" in the future-work section.

Decision 2: Vision model for image-heavy PDFs?

Gemini Flash at $2.50–12.50 is almost free. The question is whether the CA3 rubric rewards this level of catalogue sophistication, or whether demonstrating the architecture (the pipeline design, the handoff, the live data connection) carries more weight than an exhaustively tagged catalogue. If the rubric favours architecture, build the pipeline to handle image-heavy PDFs but only run it on a representative sample (50–100 files) for the demo.

This avoids bolting on an artificial API call unrelated to the core problem.

10. Reference Taxonomies — Tying Resources to Curriculum Outcomes

The missing dimension

Everything up to this point has been about describing what a resource is — its subject, format, grade band, season. But a teacher doesn't search by resource attributes. A teacher searches by need: "I'm teaching 2nd class, strand unit 'Place Value', what do I have?" or "I need a UFLI lesson 42 activity for my SET group."

This requires a fundamentally different tagging dimension: curriculum outcome alignment. Resources get tagged not just by what they are, but by what curriculum outcome they serve. This unlocks two capabilities the project brief explicitly asks for:

  1. Outcome-to-resource mapping: Given a curriculum outcome code, return matching resources
  2. Gap detection: Iterate all outcomes, identify those with zero matching resources, and trigger the Maker agent to generate content for those gaps

Two regimes, one system

The Irish primary curriculum is in transition. Some subjects use the 1999 framework (no structured outcome codes), others use the new framework with coded outcomes. The system must handle both.

  2. Pass 2: Curriculum alignment — send resource text + reference taxonomy to DeepSeek with the prompt: "Here is a teaching resource and a curriculum taxonomy. Which outcome(s) does this resource serve? Return JSON with outcome codes and confidence."

Gap analysis as a CA3 rubric win

Curriculum gap detection maps directly to the CA3 brief's core requirements:

  • Handoff & Orchestration (25%): The Researcher agent ingests the reference taxonomy and resource catalogue, identifies gaps, and hands a structured gap list to the Maker. Each gap is a real input to the next agent — not a loosely related task.
  • Strategic Rationale: Naming the two-curriculum-regime problem (1999 vs. new framework) and designing a synthetic coding scheme for the older one is exactly the kind of domain-specific reasoning the rubric rewards.
  • Regulatory/Ethics: The gap detection process itself is a quality-assurance mechanism — it prevents the system from claiming coverage it doesn't have, which is a trust-calibration move straight out of Week 2 (Lee & See, 2004).
  • Live data: The reference taxonomies and the catalogue are both queryable at run time via the Google Sheet (or lightweight DB) — two live data sources, not one.

11. Gap Filling — Create, Describe, or Discover?

When the catalogue comes up empty

Once the gap detection engine (Section 10) identifies that an outcome has zero matching resources, the system must do something useful. The project brief is deliberately flexible: "content generation will at least be creation of lesson plans that bridge curriculum/outcomes and content/methods to fulfil; stretch will be new content creation if easy enough." So the real question is: what tier of response is both useful to a teacher and safe to build?

Why lesson plans are the sweet spot for CA3

  • LLMs excel at structured text: A lesson plan is a template with predictable sections (objective, warm-up, main activity, plenary, differentiation, assessment). Models produce these reliably because the format is well-represented in training data.
  • Low hallucination surface: The learning objective comes directly from the curriculum outcome prose — the model isn't inventing it, it's restating and contextualising it. Activities can reference catalogue exemplars rather than being invented from scratch.
  • Natural quality gate: A teacher can scan a lesson plan in 30 seconds and judge its usefulness. A badly-generated worksheet might have subtle errors that take longer to spot.
  • Directly fulfils the brief: "Creation of lesson plans that bridge curriculum/outcomes and content/methods to fulfil" is the brief's own baseline. Anything beyond this is the brief's own "stretch."
  • Maps to rubric: The Maker agent receives a structured gap (from Researcher) → produces a structured lesson plan (handoff to QA/Communicator) → the plan references specific catalogue resources. This is a clean, demonstrable pipeline.

Two practical design questions shape the run-time architecture: how does a web-based solution access a catalogue that lives in a private OneDrive folder? And what does the teacher actually receive at the end of a query?

Why Google Sheets satisfies the live-data requirement

The CA3 brief requires "at least one agent must connect to a live external data source via a genuine tool call/MCP/API query at run time — not hardcoded, cached, or copy-pasted (verified in the submitted code, not just claimed)."

A Google Sheet accessed via the Sheets API v4 satisfies this directly:

  • Real API call: The Researcher agent makes sheets.spreadsheets.values.get requests with a filter/query parameter. This is authenticatable, loggable, and demonstrable in the submitted code.
  • Write-back: The Maker and Communicator agents write back to the Sheet — new resource rows, gap flags, generated lesson plans. The Sheet is the system of record, not a read-only mirror.
  • Teacher-facing: The Sheet is also the teacher's manual interface. They can browse all resources, edit tags, add notes, and see what the agents have done — all without touching the web UI. This is trust calibration in action (Week 2 — Lee & See, 2004): the system's reasoning is visible and editable.
  • Free tier sufficient: Google Sheets API has a generous free quota (60 requests per minute per user, 500 requests per 100 seconds per project). More than enough for a single-teacher CA3 demo.

The project brief itself suggested this: "A live, queryable resource catalogue (e.g. a Google Sheet or lightweight database) that agents write to and read from at run time; this also serves as the project's live-data technical requirement."

14. Two Agent Teams — Build vs. Operate

Why the same agent archetype produces genuinely different agents in different contexts

The project brief proposes two distinct agent teams: one to develop the solution, one to operate it. At first glance this looked like over-engineering for a CA3 demo — the build work (populate catalogue, author taxonomies, deploy Worker) seemed like deterministic setup, not agentic work. But the split is correct, and the reasoning sits at the heart of the module's own teaching.

The module's agent template says: agents are domain-specific, not generic

From Week 4's recurring class exercise: an agent is defined as a single markdown file with a clear identity, a specific team role, 4–6 core beliefs, a communication style, explicit boundaries, and at least one performable skill. The Five Innovators — Researcher, Designer, Maker, Communicator, Manager — are roles, not interchangeable tools. The same role filled with different domain expertise produces a genuinely different agent.

A Researcher that researches Cloudflare Worker patterns, Graph API endpoints, and JSZip library options has fundamentally different domain expertise, beliefs, boundaries, and performable skills than a Researcher that queries an Excel catalogue for UFLI-aligned phonics resources. Same role. Different agent. Different system prompt. Different output. This is exactly what the module teaches — the agent is the role plus the domain, not the role alone.

Entry Point 1 — "I know my outcome"

Entry Point 2 — "I remember a resource"

Mode: Content-directed. Free-text, fuzzy, description-based.

UX: A single prominent search box with placeholder text: "Describe the resource you're looking for — any detail helps." No dropdowns, no taxonomy. The teacher types what they remember: colour, theme, activity type, a stray keyword from the filename, anything.

Backend behaviour: The query is sent to the Worker, which runs it through the Researcher agent with a different system prompt: "Match this free-text description against resource metadata (filename, content description, tags). No lesson plans are generated. The system is in pure-retrieval mode.

Example query: "blue balloons, I think it was phonics, maybe CVC words"

Entry Point 3 — "Surprise me"

Mode: Exploratory browsing. Filterable catalogue tiles.

UX: A visual grid of filter chips representing the primary tag dimensions: Subject, Grade band, Format, Season. Selecting a chip narrows the visible resources. Selecting multiple chips intersects them. Results appear below as cards (filename, format icon, key tags, a one-line content description). No taxonomy guidance, no free-text parsing — just direct catalogue exploration.

Key design decisions behind the wireframe

  • Mode tabs at the top, not buried in a menu. The three modes are fundamentally different mental models for the teacher. Making them visible as tabs signals that the system supports all three, and switching is cheap.
  • Curriculum dropdowns only appear in curriculum mode. Content-search and browse modes don't show them — reducing cognitive load when the teacher isn't thinking in curriculum terms.
  • AI-generated content is visually distinct (the 🤖 badge, different card border) but lives in the same results list as catalogue resources. The teacher treats them the same way — thumbs up, thumbs down, bundle or exclude. The system is transparent about provenance without segregating the experience.
  • Gaps are called out but don't block the flow. The teacher can ignore a gap and bundle what exists, or click to generate. The system doesn't force action.
  • The refinement bar accepts both structured chips and free-text. Structured chips (format, grade, pedagogy) are instant client-side filters. Free-text ("nothing that needs laminating") is sent to the Worker for semantic interpretation — slower but handles the unpredictable stuff teachers actually say.
  • The bundle button is always visible, always shows a count, and is always a deliberate action. No auto-download, no "you might also want..." upsells. The teacher decides when they're done.
  • Disagreement actions are per-resource, not buried in a settings panel. This keeps the refinement loop tight — the teacher stays in the results view, making quick judgments, rather than navigating away to configure filters.

Seven numbered decisions — push back on any of them

Decision 1: Parse depth — how much of the catalogue gets deep-parsed?

The tagging exploration (Sections 3–6) proved that full deep parse of all ~3,300 PDFs is trivially cheap: ~$5–16 total API spend, ~90 minutes processing time. The cost argument for an optimised sample no longer applies — there is no meaningful time or money saving from skipping files. The catalogue is the product; an honest catalogue needs honest tagging.

For text-rich PDFs (~70%): pdfplumber text extraction → DeepSeek classification → 6–8 structured tags per file. For image-heavy PDFs (~30%): Gemini Flash vision → direct tag inference from visual content. This catches activity type, grade band, and pedagogical intent that text extraction alone misses from worksheets, craft templates, and posters.

→ Decision: Deep-parse all PDFs in-scope. Text-rich via DeepSeek (~$3). Image-heavy via Gemini Flash vision (~$3–13). The confidence column still records parse method: 0.9 = content-parsed, 0.5 = folder-only (for non-PDF files). Total: ~$6–16, ~90 minutes.

Decision 2: Subject scope — which subjects, and should we trim the catalogue?

The Irish primary curriculum spans Language (English + Gaeilge), Mathematics, SESE (Science, Geography, History), SPHE, PE, and Arts Education. Building outcome-level mapping for all of them is rote transcription, not engineering insight. The two-regime problem — coded outcomes (TF codes) vs. progression continua (PC1–PC12) — is fully demonstrable with just Language + Maths. Adding more subjects proves endurance, not understanding.

If we scope the reference taxonomy to English + Maths, should we also trim the catalogue to only those subjects? There is a strong argument for yes: a catalogue of 4,400 files with only ~1,800 actually mapped to outcomes creates a misleading demo (most queries return zero results because the files exist but aren't mapped). A trimmed catalogue of ~1,800 English + Maths files where every file has deep tags and outcome mapping tells a cleaner story. The brief itself says "It also will target a limited content catalogue, aiming to establish credibility rather than delivering a broad solution."

Note: some folders are cross-curricular. A Christmas phonics worksheet lives in xmas/ but is literacy content. The trim should be by inferred subject (from content analysis), not by folder path. Seasonal folders, back-to-school packs, and fun-stuff resources that are fundamentally literacy or numeracy stay in scope.

→ Decision: Scope reference taxonomies to Primary Language (English, TF codes) + Primary Mathematics (PC continua). Trim the catalogue to files whose content infers English or Maths as primary subject. Others tagged from folder only and excluded from demo queries. Estimated catalogue size after trim: ~1,800–2,200 files.

Decision 3: No Gaeilge — exclusion as domain awareness

LLMs are materially weaker in Irish — grammatical errors, dialect mismatches, unnatural phrasing. Generating Irish-language educational content with an LLM is an active research problem, not a CA3 deliverable. The ~119 Gaeilge files in the catalogue are tagged as subject=Gaeilge from folder name and excluded from the trimmed catalogue per Decision 2. Naming this as a deliberate exclusion with the specific reasoning demonstrates you understand AI limitations, not that you forgot about Gaeilge. The exclusion is itself a trust-calibration move (Week 2 — Lee & See, 2004): don't claim capability you can't deliver.

→ Decision: Exclude Gaeilge from the trimmed catalogue, outcome mapping, deep parsing, and demo queries. Name the reasoning explicitly in the writeup.

Decision 4: UFLI programme reference — what it is and why it matters

What UFLI is: UFLI Foundations is a structured phonics programme from the University of Florida Literacy Institute. It has 128 lessons in a specific scope-and-sequence — Lesson 1 starts with short 'a' CVC words, Lesson 54 introduces the VCe a_e pattern ("cake," "gate"), and so on through affixes and advanced word study by Lesson 128. Each lesson is a known, fixed point on a progression.

Why it matters for Teacher's Pet: The teacher's collection contains 24 UFLI-aligned resources (worksheets, word-work mats, decodable passages, games). Many are already filename-tagged with lesson numbers (e.g. "UFLI 54-62 Word Work - Korotney.pdf"). If we author the UFLI scope-and-sequence as a JSON taxonomy — 128 entries, each with lesson number, focus description, and which sounds are in play — the system can:

  • Respond to the query "I need resources for UFLI Lesson 54" by matching programme_ref="UFLI/L54" in the catalogue
  • Know that Lesson 54 = VCe a_e pattern and cross-reference it to the Language Curriculum outcome TF4 (Phonics/word recognition) at Stage 2
  • Prevent generated lesson plans from accidentally using sounds from later, untaught lessons (a real risk with LLM generation)
  • Suggest adjacent-lesson resources as fallbacks: "No resources for Lesson 54, but you have 3 resources for Lessons 53 and 55 that target similar patterns"

This is a separate reference layer from curriculum outcomes. A resource can be tagged to both: outcome_code=TF4,C2 AND programme_ref=UFLI/L54. The teacher can search by either.

→ Decision: Author the full UFLI Foundations scope-and-sequence (128 lessons) as a JSON taxonomy. Map the 24 UFLI-aligned resources by lesson number. Numicon and morphology plan taxonomies stay as JSON skeletons — not wired into active demo matching.

Decision 5: Gap filling — search first, generate as fallback

The original design had Maker generating lesson plans for every curriculum gap. A better model respects teacher agency: the system should first try to find existing content (from trusted public sources), suggest it to the teacher for review, and only generate new content as a fallback when nothing is found.

Revised gap-flow:

  1. Catalogue match: Query the Excel catalogue for resources matching the outcome. These go straight into the bundle.
  2. Gap identified: An outcome has zero or low-confidence matches.
  3. Search for existing content: The Researcher agent queries curriculumonline.ie (one strand, one stage — narrow scope per Section 11) for public NCCA resources matching the gap. Returns titles, descriptions, and URLs.
  4. Teacher reviews: Results shown as "Found 3 public resources for this gap. Review and add to catalogue?" Teacher clicks to add → new row written to Excel → resource added to bundle. Teacher can also reject ("not what I need").
  5. Generate as fallback: If teacher rejects the suggested resources, or if nothing was found, the Maker agent generates a lesson plan (text-only markdown). This is the safety net, not the first resort.

This design is stronger than the original for three reasons: (a) it keeps the teacher in control of what enters their catalogue, (b) discovered content is NCCA-vetted so quality is higher than AI generation, (c) the search-first-then-generate flow is a more interesting agent orchestration to demonstrate — it involves conditional branching (Researcher → if found, Communicator presents; if not, Maker generates) rather than a linear pipeline.

→ Decision: Gap resolution is search-first, generate-as-fallback. Bundle contains: matched catalogue resources + teacher-approved discovered resources + generated lesson plan (only if gaps remain after discovery). Teacher reviews all additions before they enter the catalogue.

Decision 6: App-only Graph auth for the demo; name delegated auth as production fix

The demo needs zero friction to feel magical. A login popup kills the illusion. The Limitations section explains exactly what changes for production (MSAL.js, delegated permissions, content isolation) and why it matters (GDPR Art 5 data minimisation, Art 32 security). The lecturer sees you know the right answer even if you're not building it.

→ Decision: Ship the demo with app-only Graph auth in the Worker. No user login. Document delegated auth as the production path in Limitations.

Covered by Decision 1 above. No separate sample-based approach.
